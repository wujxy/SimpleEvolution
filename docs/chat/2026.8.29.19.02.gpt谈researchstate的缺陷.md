我基本赞成你对协作者的修正，而且我觉得这不是“少喂一点上下文”的工程优化，而是一个更重要的 **agent 设计原则**：

> **Harness 应该保证信息可得、位置明确、权限正确；至于履行职责需要看什么、看多少，应当由有能力的 agent 自己决定。**

从你们几次 run 的结果看，这个判断有实证支撑。executor / challenger / reviewer 并不是弱 worker；它们拿到职责、目标和世界访问能力以后，本身就会调查、搜索、验证，甚至 coding agent 单独都能把大量研究工作做完。那 Harness 再替它挑出“你应该看这 5 个 research items”，不仅多余，还有两个潜在副作用。

第一，**Harness 会悄悄成为第二个 Scientist**。它必须判断什么信息与当前协作者相关，而这本来就是研究判断。第二，**预装 context 会形成锚定**。尤其 proposer/searcher，本来可能从另一个角度理解问题，结果一上来就看到 Scientist 整理好的“open questions / dead ends”，搜索空间直接被当前 framing 圈起来。

所以我现在更认这个形态：

```text
Scientist Research Memory
        │
        │ 客观存在，可访问
        │
        ├──────── Executor
        ├──────── Challenger
        ├──────── Reviewer
        └──────── Searcher / Proposer
```

Harness 只告诉它：

> 这里存在本 run 的研究记录，它包含 Scientist 已经形成的重要认识、探索历史和相关证据；你可以并且应当在履行职责需要时自行查阅。

**不给摘要，不预选节点，不替它读。**

甚至“应该自行查看”也不必变成“开工前必须全文读取”。职责不同，专业 agent 自己判断：

- executor 做一个极窄实现，也许根本不需要翻全历史；
- challenger 如果不查 Scientist 的旧判断，大概率没尽到职责；
- reviewer 需要什么就自己追；
- de-novo proposer 可能故意只查 dead history 做查重，而不过多看 current framing。

这种裁量应该留给 agent。

---

至于提案 agent 回来的整套方案，我这次不打算跟它唱反调找存在感。**主架构我认为已经相当接近正确答案了。** 但其中有两三个地方，我会继续收紧。

### 第一，`View + Research Memory + Evidence/World` 这个三层，我认

而且我觉得现在可以明确：

**不是把现在多词条 Research State “简化成 View”。**

而是把现在这个已经工作的 Research State **重新解释为 View**。

它现在能做的东西全保留：

- Scientist 当前的物理/机制理解；
- 当前研究判断；
- 当前 remaining problem；
- 当前重要数字；
- 当前方向。

仍旧自由文本，仍旧在真正 milestone 时 revise，仍旧直接放进 Scientist 当前上下文。

它唯一失去的职责是：

> **不再负责保存所有未来可能有用的历史认知。**

这个职责交给 Research Memory。

所以这不是削弱，是把一个器官原来兼任的两个职责拆开。

---

## 第二，Research Memory 的 item 设计也基本合理，但我会继续保持“工具味”，不要“协议味”

我认这种东西：

```text
R17
content:
Timing may contain vertex information beyond radial correction.

status:
parked

evidence_refs:
executor-001

note:
Only radial formulation has been tested.
```

也认：

```text
active / parked / closed
```

因为这三个词不是在教它怎么科研，只是在帮它管理：

> 我要不要继续关注这个东西？

而且 R7 已经证明这个区别有实际价值。

但比如 `kind=findings/question/idea`、`related_to / derived_from / supersedes` 这些，我会明确降到：

> **Scientist 想用就用的描述能力。**

不要期待它每次把图维护得像 Neo4j。

最终 Research Memory 应该允许长成：

```text
R12 --related--> R17
```

也允许只是：

```text
R12:
I should revisit timing if the charge-based vertex route saturates.
```

LLM 完全能理解后者。

我们需要解决的是 **信息丢失**，不是“关系没有机器可解析”。

---

## 第三，我现在反而不太认提案 agent 那句“revision 时走查 parked 集”

这个地方我觉得它又有一点开始替 Scientist 设计科研 workflow 了。

它说：

> revise_research_state = 重写 view + 维护 memory + 自行重定价扫描 parked 集。

前两项没问题。

最后这个“扫描 parked 集”我会谨慎。

因为它很容易演化成：

```text
每次 milestone
→ list all parked
→ 每个重新评估
→ 填状态
```

然后 Scientist 又开始履行 Harness 的行政流程。

我们需要解决的问题不是：

> Scientist 不会意识到格局变化应该重新考虑过去。

目前证据更像是：

> **它想考虑的时候，那些东西已经不存在于可操作认知中了。**

R7 临终能够重新写出 TOA open question 本身就是非常好的证据：**它会想。**

缺的是中途能方便找回来。

所以我宁可先给：

```text
search_research_memory(...)
list_research_memory(...)
inspect_research_item(...)
```

并在 Scientist 的整体职责认知里让它知道：

> 这是你自己的长期研究记忆。

然后看看它自己会不会在 saturation / surprise / milestone 时使用。

只有实验证明：

> memory 明明在，它还是从来不翻，

我们才有理由进一步加“revision 时回顾历史”这样的认知习惯。

这个先后顺序很重要。

# 我觉得现在可以用一个更真实的 Scientist 工作流检查它有没有削弱能力

不是把它设计成流程，而是看真实研究自然会怎么发生。

### 一开始

Scientist 进入问题。

它照旧：

```text
看 goal
调查世界
bash / code / literature
自己理解问题
```

什么都没变。

它甚至可以前几十步完全不碰 Research Memory。

这很好。

---

### 某一刻出现一个暂时不做的好想法

例如 R7：

> timing 可能还有 radial 之外的 vertex 信息，但我现在先走 charge/pattern。

现在多一个很便宜的能力：

```text
remember(R17,
 "Timing may contain vertex information beyond radial correction",
 parked)
```

然后它继续研究。

**注意：Harness 没叫它探索 timing。**

只是它刚刚自己想出来的东西不再因为上下文滚动而死掉。

这是纯增益。

---

### Scientist 派 executor

和现在完全一样。

它写任务：

> 给我测试 timing radial correction。

Executor 收到职责和当前任务。

Research Memory 在 `.scientist/...`，它知道那里存在。

它觉得需要，就自己进去看。

Scientist 不给它装配：

> R17/R18/R23 是你必读的。

所以 executor 的自主能力完全保留。

---

### Executor 返回 radial 失败

Scientist 自己解释：

> radial formulation failed。

这时候它可能更新：

```text
R23 closed:
radial timing correction did not help
evidence executor-001
```

同时 R17：

```text
Timing may contain information beyond radial correction
```

压根不需要变化。

这里甚至不需要 formal parent/child graph。

**只要两个对象没有被压成一句话，它们就不会一起死。**

这点很重要。

我们之前差点以为必须靠 lineage 才能解决。

其实 persistent item identity 已经解决了最关键的一半。

---

### 十几个小时之后，研究格局变了

能量已经没东西挖了。

Scientist 像现在一样 revise Current View：

> energy route saturated; vertex dominates remaining gap.

然后它自己思考下一步。

现在和 R7 唯一的关键区别在于：

它如果想到：

> 我之前是不是有别的 vertex route？

可以非常廉价地：

```text
search_memory("vertex alternative timing")
```

于是 R17 回来。

**我们给的是 recall capability，不是 recall decision。**

我觉得这个边界特别漂亮。

Scientist 还是 Scientist。

---

### Challenger 进来

Scientist 说：

> challenge my current judgment.

Challenger 知道：

```text
current view 在这里
research memory 在这里
world/code/report 都在这里
```

然后自己干。

如果它够强，它可能发现：

> 你当前 View 暗示 timing 没价值，但 R23 实际只测试 radial，而 R17 仍然成立。

这比 Harness 提前给它：

```text
这里有一个可能的错误：R23 scope radial-only
```

强得多。

前一种是真的 challenger。

后一种其实是 Harness 在 challenge。

所以你这个修正我现在非常认。

---

# 这样看，新设计实际上很克制

原来的 Scientist：

```text
LLM Scientist
+ current research state
+ world
+ powerful collaborators
```

新的 Scientist：

```text
LLM Scientist
+ current research state             ← 完全保留
+ persistent research memory         ← 新增
+ world                              ← 完全保留
+ powerful collaborators             ← 完全保留
```

Research Memory 提供的也只有：

```text
记住
找回
查看
轻量更新状态
引用证据
可选关联
```

没有：

```text
替你生成 hypothesis
替你决定 frontier
替你重定价
替你选择下一步
替你判断证据
替你安排 collaborator 看什么
```

这就很像我们给 Scientist 增加了一个真正的科研工具，而不是给它套了一套科研操作系统。

---

所以我现在会稍微修改提案 agent 的最终原则，变成：

> **Current View 帮 Scientist 保持注意力；Research Memory 帮 Scientist 保存自己认为值得未来重新调用的认知；Evidence/World 保存事实。Harness 负责让这些东西持久、可检索、可引用，但不负责组织 Scientist 的研究，也不负责替协作者挑选该看的内容。**

最后这一句尤其重要：

> **协作者访问的是 Scientist 的研究环境，不是 Scientist 为它准备好的 context package。**

我觉得这个表述比“图指给席位看，不喂”还更准确。

因为它和你们目前实验里真正表现很强的 agent 使用方式是一致的：**给一个强 agent 世界、权限、职责和工具，然后相信它会做自己的工作。** Harness 该补的是它做不到的基础设施，不是替它预先完成认知。
