对，我觉得你抓到的是一个非常基础、但我们之前在 Scientist 设计里几乎没认真讨论过的层：**不是 Scientist“聪不聪明”，而是 Scientist 所站的 agent runtime 本身有没有把模型的每一秒钟用好。**

我查了 Anthropic 的公开文档和 Codex 的公开源码。结论非常明确：

> **Claude Code / Codex 的高效率不是靠一个更复杂的科研 workflow，而是靠一个非常好的“异步 ReAct runtime”。**
>
> 你们现在 Scientist 更像：
>
> `think → tool → 等 → think → tool → 等 → think`
>
> 而成熟 coding agent 更接近：
>
> `think → 发射一批独立动作 → runtime 并发执行 → 收一批结果 → think`
>
> 同时长任务则：
>
> `launch → 拿 handle → 继续干别的 → completion event / wait → consume result`

这两个差别非常大。

# 1. Claude Code 最重要的设计：一次 reasoning 可以发多个 tool call

Anthropic 官方文档明确写了：

> Claude 可以在**同一个 assistant response 中生成多个 `tool_use` block**，如果这些工具调用互相独立，宿主应该并行执行，然后**一次性把全部 `tool_result` 返回**。

也就是说并不是：

```text
Claude
 ↓
read A
 ↓
Claude
 ↓
read B
 ↓
Claude
 ↓
read C
 ↓
Claude
```

而是：

```text
                 ┌─ read A ─┐
Claude ─ tool ───┼─ read B ─┼── results ─ Claude
                 └─ read C ─┘
```

所以比如 Scientist 想：

> 我要看看 `a.cc`、`b.cc`、`config.yaml` 三个东西。

成熟 harness 允许模型在**一次 generation** 中直接输出：

```text
Read(a.cc)
Read(b.cc)
Read(config.yaml)
```

runtime 同时发出去。

等三者完成：

```text
result(a)
result(b)
result(config)
```

作为**一次 continuation** 送回模型。

### 这节省的不只是 shell 时间

更大的节省其实是 **LLM round trip**。

假设你有 8 个独立信息源。

差的 harness：

```text
LLM → tool → LLM → tool → LLM → tool ...
```

可能需要 8 次 model inference。

好的 harness：

```text
LLM
 ↓
8 tool calls
 ↓
parallel runtime
 ↓
8 results
 ↓
LLM
```

只需要 **1 次额外 reasoning boundary**。

所以 Claude Code 经常给人一种：

> “它怎么一口气干了这么多事情？”

的感觉。

不是因为 Claude 在一个 shell command 里偷偷写了很多 `&`。

而是 **tool protocol 本身支持 one-to-many。**

Anthropic 甚至专门给模型提供了 parallel-use prompting guidance，要求：

> independent tool calls 应尽可能同时发出，而不是 sequentially。

# 2. 第二层：Claude Code 的后台进程不是“等 shell 返回”

这就是你贴出来的东西里很明显的部分。

Claude Agent SDK 暴露的 `Bash` tool 本身就有：

```text
run_in_background: true
```

后台启动后返回：

```text
shellId
```

然后又提供独立工具：

```text
BashOutput(shellId)
KillBash(shellId)
```

`BashOutput` 返回的是：

```text
output
status = running | completed | failed
exitCode
```

也就是说：

```text
LLM
 ↓
Bash(long_job, background=true)
 ↓
shellId=17
 ↓
LLM继续工作
```

而不是：

```text
LLM
 ↓
Bash(long_job)
 ↓
............60 seconds............
 ↓
result
 ↓
LLM重新开始思考
```

这是一个非常本质的区别。

你贴的：

```text
until grep ...
do sleep ...
```

然后 Claude Code 同时还能：

```text
Stop Task
CronList
CronDelete
...
```

就是这种 runtime 语义带来的体验。

# 3. 所以 Claude Code 实际存在两种完全不同的 concurrency

这个一定得区分。

### A. intra-turn parallelism

一次模型输出：

```text
tool A
tool B
tool C
```

runtime：

```text
A ─────┐
B ─────┼─ await all
C ─────┘
```

然后只进行一次新的 model turn。

这是**减少 reasoning round trips**。

---

### B. inter-turn background execution

```text
launch experiment A
      │
      └── job_id=A

Scientist继续：
    grep
    read
    inspect
    launch B
    reason
    ...
```

A 在另一个 runtime task 里自己跑。

这是**避免 I/O / long-running job 阻塞认知主体**。

两个机制结合起来，才会得到 Claude Code 那种感觉。

---

# 4. Codex 的源码更有意思，因为它基本把这个设计写在明面上了

Claude Code 本体不是完整开源的，所以只能通过官方 tool API 和 Agent SDK 看它的语义。

但 Codex 是开源的。

它里面有一个很值得我们借鉴的抽象：

```rust
trait ToolExecutor {
    ...
    fn supports_parallel_tool_calls(&self) -> bool {
        false
    }
}
```

也就是说：

> **“这个 tool 能不能和其他 tool 并发”本身是 tool 的 runtime property。**

默认：

```text
parallel = false
```

而比如 shell：

```rust
fn supports_parallel_tool_calls(&self) -> bool {
    true
}
```

明确允许 parallel。

Codex 的 `exec_command` 也是：

```text
supports_parallel_tool_calls = true
``` 


web search 同样：

```text
supports_parallel_tool_calls = true
``` 


这比“prompt 里跟 Scientist 说你可以并行”强得多。

因为这里已经变成：

> **Tool contract 的一部分。**

---

# 5. 而且 Codex 从 model API 层就开启了 parallel tool calls

Codex 发 Responses API 请求的时候有：

```text
parallel_tool_calls
```

也就是说整个链路实际上是：

```text
             Model
               │
               │ parallel_tool_calls=true
               ▼
      [call1, call2, call3]
               │
               ▼
          Tool Registry
          /     |     \
       tool1  tool2  tool3
         │      │      │
         └──────┼──────┘
                ▼
           aggregated results
                │
                ▼
              Model
```

Codex 的请求构造源码里就明确带这个字段。

所以这不是 UI trick。

是**agent protocol 本身就是 batch ReAct**。

# 6. Codex 对长 command 的处理也不是简单 await

Codex 新的 `exec_command` 有一个很重要的概念：

```text
process_id
yield_time_ms
```

它会：

```text
spawn process
      │
      ├─ 很快结束 → 返回 output
      │
      └─ yield deadline 到了仍没结束
             ↓
         返回 session / process handle
```

之后可以通过：

```text
write_stdin
```

继续和这个 process 交互。

因此它的 shell runtime 本质上更像：

```text
process manager
    ├── P137
    ├── P138
    ├── P139
    └── ...
```

而不是：

```text
subprocess.run(...)
```

这是个非常大的架构差异。

---

# 7. 但这里我反而发现了 Codex 当前一个非常值得我们吸取的反面教训

Codex 的 long-running process 已经有：

```text
process id
yield
write_stdin
```

但一些情况下它仍然需要模型自己：

```text
wait
wait
wait
wait
```

去轮询。

近期 Codex issue 里有人记录了非常夸张的情况：

```text
model
→ wait
→ model
→ wait
→ model
→ wait
...
```

每一个 `wait` 又产生一次完整 model turn，导致几千万 token 被消耗在“任务到底跑完了吗”上。

Codex multi-agent 现在也有人指出类似问题：

> child 完成后消息进入 mailbox，但 idle parent 不一定自动 wake；最后仍然可能变成 `wait_agent → wait_agent`。

这个对我们的 Scientist 极其有启发。

因为：

> **异步 ≠ 让 LLM 自己轮询。**

真正正确的 runtime 应该是：

```text
Scientist launch experiment
        ↓
experiment_id=E17
        ↓
Scientist继续工作
        ↓
runtime detects E17 completed
        ↓
completion event
        ↓
Scientist receives:
    E17 completed
```

而不是：

```text
Scientist:
E17好了没？

runtime:
没

Scientist:
E17好了没？

runtime:
没

Scientist:
E17好了没？
```

# 8. 所以我现在认为我们的 Scientist 缺的不是一个“小优化”，而是一层 Execution Runtime

我们之前大量精力实际上都在：

```text
Scientist cognition
Scientist identity
research memory
proposal
experiment
node
frontier
skills
```

但底下还是一个非常原始的：

```text
              ┌─────────┐
              │Scientist│
              └────┬────┘
                   │
                one tool
                   │
                   ▼
                 await
                   │
                   ▼
              tool result
                   │
                   ▼
              Scientist
```

这意味着 Scientist 哪怕再聪明，也像一个教授：

> 每查一个文件，都亲自打电话问秘书一次，然后坐在椅子上等秘书把文件送过来，再决定下一本文件是什么。

Claude Code/Codex 则像：

> “把 A/B/C/D 四份资料一起拿过来；实验 E 放后台跑。我先看 F。”

这两个人**智商一样**，科研吞吐量也完全不同。

# 9. 我认为 Sci 最核心应该补四个 primitives

我反而不建议一开始做非常复杂的 async framework。

真正决定体验的就四个。

## ① Native multi-tool turn

允许 Scientist 一次 response：

```text
inspect(A)
inspect(B)
grep(C)
history_query(D)
```

不要逼成：

```text
inspect(A)
→ resume scientist

inspect(B)
→ resume scientist

grep(C)
→ resume scientist
```

这是第一优先级。

---

## ② Parallel-safe 是 tool property

照 Codex 这个思路我非常认可：

```text
Tool:
    parallel_safe = true / false
```

比如：

```text
read_file            true
grep                 true
history_search       true
inspect_node         true
web_search           true

git_mutate            maybe false
submit_experiment     true
workspace_transition  false
```

这样 Scientist 只负责表达：

> 我要干这四件事。

是否一起执行，是 runtime semantics。

这非常符合我们一直坚持的：

> **不要让 Scientist 去管理 harness。**

---

# 10. ③ Background job 是一等公民

不是只有 bash。

我们的科研系统尤其需要这个。

例如：

```text
submit_experiment(...)
```

应该立即返回：

```text
experiment_id = E127
status = running
```

而不是 Scientist 卡在这里。

甚至：

```text
claude(...)

web_research(...)

benchmark(...)

build(...)

evaluation(...)
```

只要可能长时间运行，都可以统一成：

```text
JobHandle
```

于是：

```text
J1 = submit experiment
J2 = ask Claude investigate architecture
J3 = run benchmark
```

三件事可以同时存在。

Scientist 本人则继续认知工作。

这其实和你之前说：

> Claude 是 Scientist 可以随便使唤的神器

完全一致。

真正的“随便使唤”不能是：

```text
ask Claude
→ Scientist 停止 5 分钟
```

而应该是：

```text
ask Claude A
ask Claude B
launch experiment C

自己继续研究 D
```

这时 Claude 才真正成为 Scientist 的**并行认知外设**。

# 11. ④ 最重要的：completion-driven，不是 polling-driven

我甚至认为这是我们可以比 Codex 当前实现做得更干净的地方。

runtime 应该维护：

```text
Running Jobs

E17  experiment       running
C8   claude task      running
B3   benchmark        running
W2   literature       completed
```

当完成时：

```text
event:
    job_id = W2
    status = completed
    digest = ...
```

然后有两种情况。

Scientist 正在 reasoning：

```text
event queued
```

等下一 reasoning boundary 注入。

Scientist idle：

```text
completion wakes Scientist
```

这样整个系统是：

```text
                       ┌── Experiment E1 ──────┐
                       │                        │
                       ├── Claude task C1 ──┐  │
                       │                    │  │
Scientist ─ launch ────┼── Search S1 ──┐   │  │
     │                 │                │   │  │
     │                 └────────────────┴───┴──┘
     │                                  │
     │ continue research                │
     │                                  ▼
     │                            completion events
     │                                  │
     └──────────────────────────────────┘
```

这才是真正意义上的 asynchronous Scientist。

# 12. 还有一个经常被忽略的效率点：tool result 也不能傻乎乎全塞回来

Codex 这里也做了：

```text
max_output_tokens
yield
incremental output
```

Claude Code 的 `BashOutput` 也允许针对后台 shell 获取状态/输出，而不是重新执行任务。

所以我们的 job 不应该是：

```text
experiment completed

<把 20MB log 塞给 Scientist>
```

而应该：

```text
experiment E17 completed
status: pass
metric: 173.2 → 161.4
changed_paths: [...]
artifact: ...
```

Scientist 如果觉得有问题：

```text
inspect_job(E17, logs=true)
```

再主动 pull。

这个其实和我们之前的 **history 按需查询** 是同一种设计哲学：

> runtime 保存全真世界；
> Scientist 默认看到足够做判断的信息；
> 需要细节时再 pull。

# 13. 因此，我会把成熟 agent 的基础 loop 概括成这个

不是传统教科书 ReAct：

```text
Thought
Action
Observation
Thought
Action
Observation
```

而应该理解为：

```text
                 ┌─────────────────┐
                 │    REASON       │
                 └────────┬────────┘
                          │
                   emit action set
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
            Tool A      Tool B      Tool C
              │           │           │
              └───────────┼───────────┘
                          │
                    observations
                          │
                          ▼
                      REASON
```

再外挂：

```text
background jobs
       │
       ├── running
       ├── running
       └── completed ───────► event mailbox
```

所以更准确应该叫：

> **Reason → Dispatch → Observe → Reason**

而不是一 Action 一 Observation 的经典 ReAct。

# 14. 这件事我认为应该和 Scientist 的“科研能力”完全解耦

这是我觉得最重要的一点。

不要写进 Scientist Charter：

> “You should batch independent tool calls.”

那只是软约束。

应该让底层天然支持：

```text
Scientist cognition
        │
        ▼
   Action Set
        │
        ▼
Dispatcher
 ├─ dependency
 ├─ parallel-safe
 ├─ resource lock
 └─ background policy
        │
        ▼
Runtime
```

Scientist 只需要学会：

> **一次把当前已经知道需要做的事情表达出来。**

这才符合我们之前一直强调的设计原则：

**Harness 提供能力，不替 Scientist 做科研判断。**

# 15. 所以回过头看你这个 r8 → r9 的例子

这里 Claude Code 给人的“丝滑感”：

```text
看 digest
stop monitor
cron list
cron delete
launch r9
background smoke
继续工作
```

背后实际上是至少四种 runtime capability 同时存在：

```text
multi-tool calls
        +
background process
        +
task handles
        +
incremental status query
```

并不是 Claude 的 reasoning 本身有什么神秘技巧。

---

我现在甚至会把这个列为 **SimpleEvolution / Scientist 下一层最值得补的基础设施之一**，优先级高于再加很多 fancy research tools。

因为目前 Scientist 很可能是：

> **一个有 Claude/Codex 级认知能力的大脑，却被接在一个 2023 年式的串行 ReAct harness 上。**

而最小版本其实不用复杂：**multi-tool response + parallel dispatcher + background job handle + completion mailbox**。这四个东西一旦有了，Scientist 的实际研究吞吐量应该会出现非常明显的变化。
