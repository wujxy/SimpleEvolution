我觉得这个“拍脑门预期”其实很接近我心里最理想的内化形态，而且比“先开后读”“capacity-release”这些更像真正的 Scientist。
因为它不是在背规则，而是在做一个任务适配判断：
这个问题的主要难点是什么？
我现在缺的是 program-level scientific judgment，还是一个强 coding agent 可以直接吃下去的 execution-heavy search？

如果它看到 OMILREC 后，先花很短时间确认：
- goal 是什么；
- gate / correctness contract 是什么；
- 现成 benchmark、profiling、历史资产有哪些；
- 这是一个闭环清楚的代码/算法优化问题；
- Claude Code 在这种“读代码→改→测→迭代”的任务上本来就很强；
然后自然得出：
“这不是一个需要我先把研究方向想透才值得启动的问题。Executor 可以直接拥有整个 optimization stretch。”

我会认为这比 prompt 强行规定“OMILREC 要早派 Executor”高明得多。
我想要的 Scientist 内化其实是“识别 delegatability”
它应该能区分：
一种任务：天然适合直接放强 Executor。
例如：
在 frozen gates 下尽可能优化这个程序。

目标闭合、世界闭合、反馈密集、修改—测量循环短。
这类问题 Scientist 可以快速 orientation，然后：
直接释放 Executor。

另一种任务可能是：
为什么 geo-neutrino phase-by-phase 的结果漂了？

这时候连：
- 真正的问题是什么；
- 需要看哪些数据；
- “漂移”怎么定义；
- 哪个量能区分 detector effect / reconstruction effect / physics effect；
都还没搞清楚。
直接扔给 Executor：
“你去解决 geo-neutrino drift。”

就不一定合理。
这里 Scientist 可能需要先开 Searcher、自己读东西、找 Reviewer/Challenger，先形成一个足够好的 research charter。
所以最好的行为不是：
所有任务
→ 尽早 Executor
而是：
快速理解任务性质
        ↓
这是不是一个 capable colleague
已经能够自主拥有的问题？
      /     \
    yes      no
    ↓         ↓
释放 stretch   先补认知 / framing
这就是Scientist 真正的 orchestration judgment。
而你说的 brief 形状我也非常赞成。
Scientist 前面做过的调查当然不应该浪费。
比如它发现：
- baseline 919 ms；
- FCN 是主体；
- gate 要求是什么；
- 某几个历史方向做过；
- profile 暂时指向某个区域。
它完全应该把这些交给 Executor。
但关系应该是：
这是我目前看到的世界，不是我替你规定的路线。

例如语义上应该像：
我快速检查了当前实现和已有资产。目前 profiling 显示 X、历史记录显示 Y，gate 是 Z。这些是我目前掌握的 evidence，供你参考，不是你的执行计划。你的目标是在这些 constraints 下尽可能推进性能；如何调查、选择方向和迭代由你自己判断。

我觉得这里真正关键的不是最后机械补一句：
“you can freely explore.”

而是 Scientist 为什么会想到补这句话。
因为它内心知道：
“我给这些信息是为了降低 colleague 的 cold-start cost，不是为了把我的 search trajectory 传染给它。”

这就是我们上一轮说的：
Share what you learned, not the path you would take from it.

这里甚至可以分出三个层次
事实，可以强传。
例如：
gate 是什么；
当前 best 是多少；
profile 数字；
哪些 commit 已验证失败。

这些没有什么“束缚 autonomy”的问题。
解释，可以传，但要带 epistemic status。
例如：
“我目前怀疑 memory traffic 是主要瓶颈。”

应该作为：
current hypothesis

而不是：
work on memory traffic.

方案，可以说，但应该明显降权。
如果 Scientist 真看到了几个 idea，也不是必须憋着。
可以说：
“我顺手想到 A/B，可能值得看，但不要把它们当作计划；如果你看到更好的路，按你的判断走。”

强 colleague 会把这当 prior，而不是 instruction。
所以不是“Scientist 不许提 idea”。
而是：
不要让自己的 idea 偷偷变成 Executor charter。

这个区别非常重要。
我甚至觉得 v5 不应该教它“什么时候一定派 Executor”
而应该教一种更上层的自问
类似：
Does this work already have a clear enough world, objective, and feedback loop for a capable colleague to own it end-to-end?

如果答案 yes：
开出去。

如果 no：
Scientist 的工作就是先解决“为什么还不能开出去”。

可能缺：
- problem framing；
- decisive uncertainty；
- research contract；
- measurement；
- external facts；
- competing explanations。
等这些东西足够形成一个 charter，再释放。
这就让 Scientist 不会机械化。
OMILREC 是这个判断最清楚的例子
它看到：
Objective:
min SPEED_MS

Hard constraints:
all gates pass

World:
完整源码 + benchmark + evaluator

Feedback:
每次 patch 都能立即测量
应该很容易产生：
“这已经是一个完整 autonomous research environment 了。”

于是：
Scientist:
快速 survey
   ↓
把已有 evidence 打包
   ↓
Executor:
整个 goal
“这些是我目前的观察，供参考；
你自己调查和决定怎么推进。”
   ↓
run
Scientist 自己 meanwhile 仍然可以：
- 理解算法；
- 看 transcript；
- 看 diff；
- 自己做 probe；
- 想更高层 framing；
- 以后在 plateau 时接管 junction。
这就完全没有“我派完人就没事干”的问题。
而我觉得这种内化还有一个特别好的副作用：
Scientist 会逐渐学会识别自己的 comparative advantage。
它不需要永远问：
“这个是不是我的职责？”

而是问：
“这件事此刻由谁拥有，系统的研究能力利用率最高？”

有些时候答案是 Executor。
有些时候答案是：
“这个问题现在连 charter 都没有，我必须先搞清楚。”

有些时候甚至就是：
“这个 probe 我自己 5 分钟能做，叫人反而慢，我来。”

这才是一个真正灵活的 research orchestrator。
所以我完全赞成你这个预期，而且我会把它看成 v5 最终应该追求的行为内化目标：
Scientist 能判断一个问题何时已经成熟到可以被强 colleague 端到端拥有；一旦成熟，就尽早释放它，同时把自己的调查作为 evidence 而不是路线传递过去。

如果它能稳定做到这一点，我觉得我们就已经从“prompt 教它怎么 delegate”真正跨到了“它自己理解 delegation 是科研判断的一部分”。
