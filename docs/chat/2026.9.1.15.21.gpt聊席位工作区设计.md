我也觉得现在这套有点过度设计了。问题不只是“文件夹多”，而是它把三个本来应该独立的维度绑在了一起：
1. 你是谁：Proposer / Challenger / Reviewer / Searcher / Executor
2. 你能看什么：live world、memory、ledger、external knowledge
3. 你能改什么世界：current / isolated / none
现在基本变成了“角色一换，工作区拓扑也跟着换”。这会让 Scientist 逐渐学成：
“开 Challenger = 开一种 Challenger 世界”
“开 Proposer = 再复制一个世界”
“开 Reviewer = 再搞一个带账本的世界”

而不是：
“我现在缺的是反方观点，所以叫 Challenger 来看同一个研究问题。”

这两种心智完全不同。
我会建议做一个很大的简化：
核心原则：Seat ≠ World
席位只是认知职责。
World 是研究对象。
不要让每个 seat 天生拥有自己的 world。
我会把整个系统压成只有两种真正的 world
1. Live World
就是当前 accepted research world。
只有主线 Executor 可以直接改它：
Live World
   ↑↓
Mainline Executor
Scientist、Proposer、Challenger、Reviewer、Searcher 都可以读它。
默认没有什么：
proposer world
challenger world
reviewer world

大家看到的是同一个现实。
这其实更符合科学研究本身。
如果 Scientist 说：
“Challenger，你来攻击一下我们认为 accumulation 是瓶颈这个判断。”

那 Challenger 最合理的事情是直接：
- 看当前代码；
- 看 benchmark；
- 看相关 commits；
- 看 Scientist 给它的 claim/evidence；
然后形成独立判断。
为什么它需要复制一整个 repo 才能思考？
不需要。
2. Experimental World
只有当有人真的需要改变世界来验证一个不同 world 时才创建。
例如：
Live World
    │
    ├── mainline executor → directly modifies live world
    │
    └── isolated experiment
             ↓
       disposable child world
这个 isolated world 的存在理由不是：
“这是 Proposer 的世界。”

而是：
“我们现在真的要测试一个 alternative world。”

所以它应该属于 experiment，而不是属于 seat。
这一下会简单很多。
那五个席位怎么办？
我会改成这样。
Scientist
看：
- live world；
- reports；
- memory；
- ledger；
- 必要外部信息。
自己没有专属 world。
它就是站在研究现场。
Executor
这是唯一特殊的。
mainline Executor
workspace = live world
持续改变 accepted world。
speculative Executor
workspace = isolated experimental world
验证 alternative world。
所以只有 Executor 真正需要 world ownership。
这也正好符合我们之前定下的三层结构：
Executor 是唯一 sustained world-changing seat。

Proposer
默认：
read live world
+ own session
+ maybe tiny scratch
不需要 child world。
它的职责是：
找新的解释 / mechanism / basin。

它完全可以：
- grep；
- 看代码；
- 跑已有 benchmark；
- 读数据；
- 甚至写一些临时 analysis script；
但这些都不意味着：
给它复制一个完整研究世界。

如果它想到一个真正需要改代码验证的 proposal：
那就提交给 Executor。

这反而会让角色边界更自然：
Proposer sees possibility
        ↓
Scientist judges worth testing
        ↓
Executor creates alternative world
而不是 Proposer 自己偷偷变成半个 Executor。
Challenger
一样。
它需要的是：
live world
+ Scientist current claim
+ supporting evidence
然后攻击它。
它并不需要独立 world。
事实上，我甚至觉得让 Challenger 一开始就进一个 fork 有一点概念上不对：
它攻击的是当前现实里的判断。

那就应该盯着 current reality 看。
如果它说：
“我怀疑这个结论，必须做这个 counter-experiment 才能区分。”

很好。
再让 Executor 开 isolated experiment。
Reviewer
Reviewer 更明显不需要 fork。
它真正应该拥有的是：
live world
+ research history
+ reports
+ memory
+ trajectory
它是长程观察者。
给它复制一棵 repository，除了文件系统隔离之外几乎没有概念价值。
Searcher
甚至更简单：
external search
+ optional access to live world
+ scratch
如果查文献，根本不要 repo。
如果调查：
“当前实现里 XXX 是怎么处理的？”

直接读 live world。
为什么还要 none/node/lab 三档？
我第一反应就是：
Scientist 不应该需要知道这么多 workspace 类型。
这已经开始像 Kubernetes 了（笑）。
所以我认为现在的核心问题是：你们把 safety boundary 做成了 research semantics
最初 fork 的理由其实很好：
Cognitive seat 拿到了 shell，我又不想让它破坏 live world。

这是工程安全问题。
后来慢慢长成了：
Proposer 天生在 fork world。
Challenger 天生在 fork world。
Reviewer 天生在 fork world。

这就从 safety implementation 升格成了 agent ontology。
我觉得这一步不应该发生。
正确的抽象应该是：
所有 cognitive seats 默认 read-only 接触 live world。

怎么实现 read-only，是 harness 自己的问题：
- filesystem permissions；
- git worktree read-only；
- container bind mount；
- tool permission；
- whatever。
Scientist 不应该因此学会五种 world topology。
我甚至会再进一步：认知席位最好不要有“workspace ownership”
这是我现在最喜欢的结构：
                    LIVE WORLD
                        │
        ┌───────────────┼───────────────┐
        │               │               │
    Scientist        Proposer       Challenger
        │               │               │
        ├────────── Reviewer ────────────┤
        │               │               │
        └──────────── Searcher ──────────┘
                        │
                     read only

                        │
                        ▼
                    Scientist
                     judgment
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
      Mainline Executor      Speculative Executor
              │                   │
          Live World         Child World
这非常干净。
认知席位：
ways of seeing the world

Executor：
ways of changing the world

这和我们之前定下的职责结构其实比当前实现更一致。
那认知席位如果想自己跑小实验怎么办？
这里不要因为简化又把它们锁死。
我会允许一种很轻的东西：
ephemeral scratch
比如：
- 写 Python；
- 处理数据；
- 编译一个小 reproducer；
- 做静态分析；
- 做小计算；
- 建临时文件。
但是：
scratch ≠ research world。

比如：
seat scratch:
/tmp/seat-123/
它随便折腾。
如果它需要修改真实项目代码并评价一个 candidate world，那这个动作已经在语义上成为：
experiment

这时候就应该升级为 isolated Executor / experiment world。
这样边界是行为语义，不是角色禁令。
这样 .scientist 那个虫子也自然消失
现在你们出现：
.scientist/
 ├─ records
 ├─ assistant bodies
 └─ child worlds
本质就是因为seat 身份、research state、workspace topology 混在一起了。
如果按上面的简化：
.scientist/
    memory/
    reports/
    wire/
    judgments/
只存研究认知和记录。
然后：
.work/
    experiments/
       exp-001/
       exp-002/
只在真的需要 alternative world 时才出现。
甚至 .seats/ 都未必需要持久存在。
seat session 存哪里只是 runtime 细节。
一下子哲学和目录结构就一致了：
.scientist = mind / record
world = reality
experiment workspace = temporary alternative reality

这个比现在干净得多。
我尤其不喜欢当前设计的三个地方
1. Proposer/Challenger 自动 fork
我觉得没必要。
它们的价值是独立认知，不是独立文件系统。
epistemic independence ≠ filesystem independence。
open Proposer 不继承 Scientist 的 current judgment，这才是真正的 independence。
有没有 repo copy 根本是另一回事。
2. Searcher 三档 workspace
none / node / lab 我觉得就是典型的 harness complexity leakage。
Searcher 应该只知道：
“我要查这个事实。”

至于它是否需要 repo，由系统给它 read access 就好了。
不应该让 Scientist 还要思考：
这个 Searcher 用 node 还是 lab？

这种 decision 对 scientific judgment 几乎没有价值。
3. Reviewer fork + ledger packing
这最明显。
Reviewer 的研究对象就是：
live research world + research record。

结果为了隔离给它复制 world，再为了让它看历史把 ledger 打包进去，最后出现：
body inside diary inside body

这种递归 bug。
这通常就是抽象层次不对的信号。
Reviewer 完全可以直接：
read-only live world
+ read-only research record
+ own fresh context
完事。
最终我会把整个 workspace 设计压成一个非常简单的规则
甚至只需要记这一句话：
Seats do not get worlds. Experiments do.

然后：
Scientist / Searcher / Proposer / Challenger / Reviewer
→ read the live world
→ own only context + scratch

Executor mainline
→ writes live world

Executor speculative
→ writes an isolated experimental world
如果以后某个 Challenger 真的需要亲自 world-changing experimental investigation：
那一刻它不是因为“Challenger 可以写”，而是因为它发起了一个 experiment。

Harness 可以临时给它一个 experiment workspace，或者让它召 Executor。
两种都行。
这样做还有一个你刚才担心的巨大好处：
减少了对 agent 行为的预先规定。
现在是：
你叫 Proposer，所以给你这种 world；
你叫 Searcher，所以你有三种模式；
你叫 Reviewer，所以给你特殊 history fork。

简化之后变成：
你是谁，只决定你为什么来。
你需要什么资源，由你实际在做什么决定。

这就给 Scientist 和各席位留下更多自由度。
所以我的判断很明确：
当前设计功能齐，但 workspace matrix 确实开始过拟合角色体系了。
如果是我，我会趁现在系统还没更复杂，往回砍一刀：
角色和世界解耦；只有实验产生子世界。

这可能是比“把 .scientist/scratch 搬到 .seats/”更值得做的结构性修正。后者只是把虫子搬家，前者是在消掉虫子的产生原因。




 





认知席位如果自己也会想要去动手做验证做实验修改的话怎么办













这正是我不想把认知席位做成“只读顾问”的原因。Proposer / Challenger / Reviewer 如果不能亲手验证，反而会被阉割。
所以我上一条说“Seats do not get worlds. Experiments do.”，并不是说认知席位不能做实验，而是说：
不要因为它叫 Challenger，就预先给它一个 Challenger world；当它真的需要做实验时，再为这个 experiment 创建一个临时 world。

这两个区别很大。
我会把认知席位的能力设计成一个很自然的渐进层级，而不是角色权限矩阵。
第一层：直接看 live world
所有席位默认都可以：
- grep / read code；
- 看 diff；
- 跑现有 benchmark；
- 跑已有 tests；
- 读数据；
- 查历史；
- 做静态分析。
比如 Challenger 怀疑：
“你们认为 accumulation 是瓶颈，可能只是 benchmark artifact。”

它完全应该自己去看 benchmark、profile、实现，而不是只坐在那里写评论。
第二层：自己的 scratch
如果它想快速验证一个想法：
- 写 Python；
- 写一个 microbenchmark；
- 编译一个小 reproducer；
- 处理结果；
- 做数学验证；
直接在自己的临时 scratch 里干。
这不需要复制整个研究 world。
第三层：需要修改项目时，按需创建 experimental world
这才是关键。
比如 Challenger 想验证：
“如果把这一层 cache 完全拿掉，所谓 bottleneck 就消失了。”

它需要真正改 src/。
那就：
Challenger
    │
    │ needs a world-changing test
    ▼
create experiment workspace
    │
    ▼
modify / compile / benchmark
    │
    ▼
evidence + diff
    │
    ▼
Scientist
这个 world 属于：
experiment-017

而不是：
challenger-003

这就是我想砍掉复杂度的核心。
也就是说：认知席位可以“动手”，但不因此变成 Executor
这里很容易混。
我不认为：
一旦 Challenger 写代码，它就越权变成 Executor。

角色应该由为什么做这件事定义，而不是由“有没有敲代码”定义。
比如：
Challenger
为了攻击一个 claim，写 50 行代码做 counterexample。
仍然是 Challenger。
Proposer
为了确认自己提出的新机制不是空想，做一个 cheap prototype。
仍然是 Proposer。
Searcher
为了确认某个第三方算法在当前数据上到底是什么性质，写一个 reproducer。
仍然是 Searcher。
Reviewer
发现历史里的一个关键结论可能 measurement 有问题，于是重跑一个 discriminating test。
仍然是 Reviewer。
认知席位不是 PPT 顾问。
它们是 researcher。
那 Executor 到底特殊在哪里？
不是“只有 Executor 能写代码”。
真正特殊的是：
Executor 可以拥有 sustained world-changing research。

这是完全不同的尺度。
比如 Proposer：
“我有个想法：把 accumulation 改成 active-window associative structure。”

它可以自己做：
快速 prototype
→ 证明大概能工作
→ 得到 20% 潜力的证据
很好。
但是如果接下来需要：
重构数据结构
→ debug
→ 处理 correctness
→ benchmark 四组输入
→ 优化 cache
→ 再想第二版
→ 再测
→ 继续几个小时
这已经不再只是：
“验证 proposal 值不值得存在。”

而是在形成一个 research stretch。
此时最自然的是：
Proposer evidence
       ↓
Scientist: this direction deserves a stretch
       ↓
Executor
       ↓
sustained autonomous research
所以边界不是：
cognitive seat = think
executor = do

而是：
cognitive seat = investigate for a particular epistemic purpose
executor = own sustained pursuit of a research charter

这个我觉得漂亮得多。
可以用一个很简单的例子
Scientist 当前认为：
XSBench 已经接近 8M plausibility ceiling。

开 Challenger：
攻击这个判断。

Challenger 可以：
读 benchmark
↓
发现 ceiling 来自某个假设
↓
自己写一个 quick experiment
↓
isolated 修改统计逻辑
↓
跑 5 分钟
↓
发现 8M 并不是物理 ceiling，而是当前 measurement contract 导致
↓
报告
完美。
它不需要：
“我不能动代码，得再叫 Executor。”

这种 agent bureaucracy 很蠢。
但是如果 Challenger 发现：
“有一整套 alternative accumulation architecture 可能突破 ceiling，我接下来需要几个小时实现。”

那 Scientist 可以说：
很好，这已经不是为了 attack claim 做一个 discriminating experiment，而是出现了一条值得自主发展的 research line。

然后交给 Executor。
所以 world 设计可以非常简单
我现在会定成三种资源，不是五种角色 world。
1. Live World
   当前真实研究世界
   everyone can inspect
   mainline owner can modify

2. Scratch
   每个 seat 都可以有
   随便写临时脚本 / reproducer / analysis
   不代表一个 candidate research world

3. Experiment World
   按需创建
   谁需要验证 world-changing hypothesis 谁就用
   disposable / isolated
注意第三个：
任何 seat 都可以请求一个 Experiment World。

不是只有 Executor。
这样 Scientist 根本不用记：
Searcher none/node/lab
Proposer fork
Challenger fork
Reviewer fork
Executor current/isolated
它只需要想：
这个 researcher 现在需要看现实、做 scratch，还是需要一个隔离实验？

简单太多。
然后只保留一个特殊 ownership：mainline
这是 Executor 真正与其他席位不同的地方。
                   Live World
                       │
               Mainline Executor
              sustained ownership
认知席位通常不会持续拥有 live world。
它们即使做 world-changing experiment，也是：
             Experiment World
                    │
              cognitive seat
              short investigation
                    │
                evidence
如果实验长成了一条真正值得持续发展的线：
promote it to an Executor stretch.

这甚至可以成为一个很自然的概念：
probe → stretch promotion
Challenger / Proposer
      │
      │ quick experiment
      ▼
interesting evidence
      │
      ▼
Scientist judgment:
"this deserves sustained ownership"
      │
      ▼
Executor stretch
这比提前限制“谁能做什么”舒服太多。
我觉得最重要的一点是：不要用 filesystem 来定义科研角色
这是当前设计最容易走偏的地方。
不要：
Challenger 因为是 Challenger，所以给 fork。

而应该：
Challenger 因为现在需要修改世界验证 claim，所以给 experiment workspace。

同理，如果 Proposer 只是读代码想 idea：
根本不创建 world。

如果 Reviewer 只是看历史：
也根本不创建 world。

如果 Searcher 临时需要编译一个算法：
scratch 足够。

资源由行为需要决定，不由角色名称决定。
这恰好也回应了你最开始的担忧：
功能越多会不会限制 Scientist 和席位发挥？

会。
所以不要设计“每个角色有哪些固定动作”。
给它们很宽的 researcher capability，然后只把真正重要的语义钉住：
- live world 是当前现实；
- scratch 是临时思考；
- experiment world 是可弃的 alternative reality；
- sustained mainline ownership 是 Executor 的特殊责任；
- Scientist 决定什么时候一个 probe 已经值得升级成 stretch。
我觉得这样既不会把认知席位变成嘴炮 agent，也不会重新长回那个复杂的 workspace matrix。
