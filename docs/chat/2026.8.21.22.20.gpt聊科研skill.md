有，而且我觉得这里其实碰到了 SimpleEvolution 里一个很重要的架构选择：

**Transformation 不一定应该是 Harness 强制调用的 tool，它完全可以被设计成 Scientist 的一种“research skill”。**

甚至我觉得从你刚才“小课题组”的类比看，skill 比 tool 更自然。

---

## 为什么不是 tool？

tool 的语义通常是：

> 外部能力调用

比如：

```text
search()
run_experiment()
read_history()
```

它解决：

> Scientist 缺什么操作能力？

但是 transformation 解决的是：

> Scientist 怎么改变自己的思考方式？

这更像人的研究能力。

一个博士生不是因为导师按钮存在才思考：

> 我是不是应该换一个角度？

而是长期训练形成的一套科研 skill。


所以：

```
Tool:
    "调用导师"

Skill:
    "知道什么时候需要找导师，以及如何向导师描述问题"
```

这两个层次不同。

---

## 我觉得可以这样拆

### Scientist 基础能力

类似 Codex / Claude Code 的 skills：

```
Scientist Skills

├── problem_decomposition
├── literature_survey
├── bottleneck_analysis
├── hypothesis_generation
├── alternative_view
├── adversarial_self_review
├── analogy_search
└── experiment_design
```

这些不是 workflow。

不是：

```
step1
step2
step3
```

而是：

> 当遇到某种认知状态时，可以调用的思维模式。


现在已经有不少开源方向在探索这种 skill layer，例如 AI Research-SKILLs 这类项目，把研究能力拆成可加载的 skill，包括 ideation、creative thinking、paper writing 等类别。  
也有专门的 scientific brainstorming skill，把 brainstorming 定义为产生候选方向，而不是验证 hypothesis，并强调 ideation 与 evidence assessment 分离。

---

## 那 Transformation 应该属于哪类 skill？

我觉得它应该是：

```
Cognitive Transformation Skills
```

不是普通 research skill。

例如：

### G1: Challenge Assumption

输入：

```
Current ResearchState:
"lookup search is bottleneck"
```

输出：

```
What if lookup itself is unnecessary?
```

---

### G2: Change Abstraction Level

输入：

```
optimize function X
```

输出：

```
why does function X exist?
```

---

### G3: Invert Objective

输入：

```
speed optimization
```

输出：

```
what constraint is causing this speed requirement?
```

---

### G4: Cross-domain Analogy

输入：

```
random memory access problem
```

输出：

```
similar to database indexing/cache hierarchy?
```

---

这些其实就是“导师经验”。

## 但是有一个关键：skill 不能直接生成 proposal

这个非常重要。

否则：

```
Transformation skill
       |
       v
new idea
       |
       v
experiment
```

又退化成：

prompt magic。


正确：

```
ResearchState
      |
      v
Transformation skill

      |
      v

新的理解框架

      |
      v

Scientist 自己重新判断

      |
      v

Proposal
```

也就是：

导师只说：

> 你有没有考虑这个角度？

不是：

> 你去做这个实验。


这和你现在设计：

> transform_worldview cannot register state or submit Proposal

是完全一致的。

Scientist 不只是改代码。

## 但是我觉得第一版不要做太多

MVP 可以非常简单：

```
skills/
├── challenge_assumption.md
├── change_abstraction.md
├── seek_alternative_mechanism.md
├── analogy_transfer.md
```

然后：

ResearchState:

```
I believe X because Y
```

触发：

```
apply skill challenge_assumption
```

得到：

```
alternative framing
```

Scientist 决定是否形成新的 ResearchState。

## 和 Codex 的 brainstorm 类比

你提 Codex brainstorm 是对的。

这类能力本质不是工具，而是 agent 的 mode。

类似：

```
Codex:

normal coding
    |
brainstorm mode
    |
plan mode
```

科研 Scientist 也可以：

```
normal research mode
    |
deep investigation mode
    |
worldview transformation mode
    |
experiment planning mode
```

但是区别：

Codex brainstorm 是为了写更好的代码。

你的 Transformation 是为了：

> 防止研究路径依赖。

---

所以我现在倾向于：

**不要把 Transformation 设计成 scheduler 调用的 tool，而是设计成 Scientist 可调用的 cognitive skill。**

Harness 只提供：

- skill registry
- skill execution boundary
- provenance recording

但是：

什么时候需要导师、选择哪个导师、是否接受建议，应该属于 Scientist 自己。

这会让你的“研究组”类比更完整：

- 学生拥有研究技能
- 导师提供思维刺激
- 实验决定生死
- 系统负责资源分配

而不是：

- Harness 按按钮让学生换思路

后者又会变成 workflow。
